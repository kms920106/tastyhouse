# 포인트(point) 도메인

## 이 도메인은 무엇인가

회원이 보유한 포인트 잔액과, 그 잔액이 오르내린 이유를 남기는 이력을 다루는 영역이다. 포인트는 주문 결제 때 현금처럼 쓸 수 있는 적립금이며, 현장 결제로 적립되거나 관리자가 직접 넣어 준다.

이 도메인의 가장 중요한 원칙은 **잔액과 이력은 항상 함께 움직인다**는 것이다. 포인트가 늘거나 줄 때마다 그 사유가 담긴 이력이 반드시 함께 남으므로, 잔액만 바뀌고 이유가 없는 상태나 이력만 있고 잔액이 안 맞는 상태는 생기지 않는다. 회원 문의나 정산 확인 시 잔액을 이력으로 되짚어 설명할 수 있어야 하기 때문이다.

## 핵심 개념

**포인트 잔액**은 회원 한 명이 지금 쓸 수 있는 포인트 총액이다. 회원별로 하나씩 존재하며, 이번 달 소멸 예정 포인트도 함께 관리한다. 포인트를 한 번도 받아 본 적 없는 회원은 잔액 정보가 아직 없는 상태이며, 처음 적립될 때 잔액 0에서 시작하는 정보가 자동으로 만들어진다.

**포인트 이력**은 잔액이 변한 사건 한 건의 기록이다. 어느 회원의 것인지, 어떤 종류의 변동인지, 얼마인지, 무엇 때문인지(사유), 언제인지를 담는다. 이력은 한 번 남으면 수정되거나 삭제되지 않는다. 잔액을 바로잡으려면 기존 이력을 고치는 대신 새로운 변동 이력을 남긴다.

**변동 종류**는 세 가지다.

| 변동 종류 | 언제 남는가 |
|---|---|
| 적립 | 포인트가 늘어날 때(현장 결제 적립, 관리자 수동 적립) |
| 사용 | 포인트가 줄어들 때(주문 결제 사용, 관리자 수동 차감, 결제 취소 시 적립분 회수) |
| 환불 | 결제가 취소되어 썼던 포인트를 되돌려받을 때 |

사용으로 기록되는 이력의 금액은 잔액이 줄었음을 나타내기 위해 마이너스 값으로 남는다.

**이번 달 소멸 예정 포인트**는 이번 달에 유효기간이 끝나 사라질 예정인 포인트 금액이다. 회원이 미리 알고 쓸 수 있도록 잔액과 함께 화면에 표시된다.

단 이 값을 채워 주는 소멸 처리가 아직 없다는 점을 알아 두어야 한다. 포인트에 유효기간을 부여해 기간이 지난 만큼을 덜어 내는 자동 작업이 서비스에 없어, 소멸 예정 금액은 계산되지 않고 항상 0으로 표시된다. 표시 자리와 항목은 준비되어 있으므로, 포인트 유효기간 정책을 실제로 운영하려면 소멸 처리를 먼저 만들어야 한다.

**사유**는 왜 이 변동이 일어났는지를 담는 설명 문구다. 시스템이 자동으로 처리하는 변동은 정해진 문구가 붙고, 관리자가 수동으로 조정할 때는 관리자가 직접 사유를 입력한다.

## 주요 업무 흐름

### 현장에서 결제하면 포인트가 적립된다

회원이 가게에서 현장 결제(현금 등)로 값을 치르고 **점주가 그 결제를 완료 처리하면** 결제 금액의 **10%**가 포인트로 적립된다. 회원이 직접 완료 처리할 수는 없어, 매장에서 값을 내기 전에는 적립되지 않는다([결정 0067](payment.md#decision-0067)). 이력에는 현장 현금 결제 적립이라는 사유와 적립률이 함께 기록되어, 나중에 얼마짜리 결제로 얼마가 붙었는지 알 수 있다.

이 적립은 결제가 완료되어 확정된 뒤에 뒤따라 처리된다. 따라서 결제 화면이 포인트 계산을 기다리며 느려지지 않는다.

적립 대상은 현장 결제뿐이다. 온라인 결제는 주문을 접수하는 시점에 이미 적립분이 계산되어 주문에 기록되므로, 결제 완료 시점에 다시 적립하지 않는다. 같은 결제로 포인트가 두 번 붙는 것을 막기 위한 구분이다.

### 회원이 주문 결제에 포인트를 쓴다

회원은 주문할 때 쓸 포인트 금액을 입력한다. 주문이 접수되는 순간 그 금액이 잔액에서 빠지고, 주문 결제 사용이라는 사유로 이력이 남는다.

보유 잔액보다 많은 금액을 쓰려 하면 포인트가 부족하다는 안내를 받고 주문이 진행되지 않는다. 잔액이 마이너스로 내려가는 일은 없다.

시스템은 회원이 화면에서 본 포인트 할인액과 서버가 처리한 금액이 같은지 대조하며, 다르면 포인트 할인 금액이 맞지 않는다는 안내를 내고 주문을 진행하지 않는다.

포인트 차감과 주문 접수는 하나의 묶음으로 처리되므로, 주문이 실패하면 포인트가 빠져나간 채 남지 않고 원래 잔액으로 되돌아간다.

### 결제가 취소되면 쓴 포인트를 돌려주고 적립분을 회수한다

결제가 취소되면 두 가지 정리가 함께 일어난다.

첫째, 그 주문에서 **썼던 포인트를 되돌려준다.** 결제 취소 환불이라는 사유로 환불 이력이 남고 잔액이 늘어난다.

둘째, 그 주문으로 **적립됐던 포인트를 회수한다.** 결제 취소 적립금 회수라는 사유로 사용 이력이 남고 잔액이 줄어든다. 여기에는 중요한 예외 처리가 있다 — 적립받은 포인트를 이미 다른 주문에 써 버려 회수할 만큼의 잔액이 남아 있지 않은 경우, **남은 잔액만큼만 차감하고 취소 처리를 실패시키지 않는다.** 잔액이 부족하다는 이유로 결제 취소 자체가 막히면 회원이 환불을 받지 못하게 되므로, 회수는 가능한 만큼만 하고 취소는 정상 진행한다는 판단이다.

두 정리는 각각 해당 금액이 0보다 클 때만 수행된다. 포인트를 쓰지 않은 주문이면 환불 처리가 없고, 적립이 없던 주문이면 회수 처리가 없다.

**환불 요청이 접수되는 시점에는 포인트를 건드리지 않는다.** 환불 요청은 아직 "요청"일 뿐이고, 실제 금전 정산은 결제가 **취소로 확정될 때** 이루어진다. 접수 시점에 포인트를 함께 움직이면 승인 전 요청만으로 잔액이 바뀌고, 이후 취소가 확정될 때 같은 금액이 한 번 더 반영되어 이중으로 환급·회수된다.

### 관리자가 포인트를 직접 넣거나 뺀다

관리자는 특정 회원에게 포인트를 수동으로 적립할 수 있다. 금액과 사유를 입력하며, 그 사유가 이력에 그대로 남아 왜 지급했는지 추적할 수 있다. 보상·보정·프로모션 등 어떤 목적이든 사유 문구로 구분된다.

수동 차감도 같은 방식이다. 금액과 사유를 입력해 회원의 포인트를 뺀다. 다만 보유 잔액보다 많은 금액은 차감할 수 없어, 잔액을 넘어서는 차감을 시도하면 포인트가 부족하다는 안내를 받고 아무것도 바뀌지 않는다.

### 회원이 자기 포인트를 확인한다

회원은 사용 가능 포인트와 이번 달 소멸 예정 포인트를 확인한다. 포인트 내역 화면에서는 그 두 숫자와 함께 적립·사용 이력 목록을 함께 본다. 주문 화면에서는 이번 주문에 쓸 수 있는 포인트 금액을 확인한다.

관리자도 특정 회원의 잔액과 이력을 조회할 수 있다. 이력은 최신순으로 보이며, 변동 종류(적립·사용·환불)로 걸러 볼 수 있고 지정하지 않으면 전체가 보인다.

## 상태와 전이 규칙

포인트에는 승인 대기나 보류 같은 중간 상태가 없다. 포인트 잔액은 숫자 하나이며, 변동이 일어나면 즉시 반영된다. 따라서 이 도메인의 규칙은 상태 전이가 아니라 **잔액이 늘고 줄어드는 계기**로 정리된다.

| 계기 | 잔액 변화 | 이력에 남는 종류 | 사유 |
|---|---|---|---|
| 현장 결제 완료 | 증가(결제 금액의 10%) | 적립 | 현장 현금 결제 적립(적립률 포함) |
| 관리자 수동 적립 | 증가 | 적립 | 관리자가 입력한 사유 |
| 결제 취소로 쓴 포인트 환급 | 증가 | 환불 | 결제 취소 환불 |
| 주문 결제 사용 | 감소 | 사용 | 주문 결제 사용 |
| 관리자 수동 차감 | 감소 | 사용 | 관리자가 입력한 사유 |
| 결제 취소로 적립분 회수 | 감소(남은 잔액 한도) | 사용 | 결제 취소 적립금 회수 |

포인트 이력은 한 번 만들어지면 바뀌지 않는다. 잘못 처리된 변동을 고쳐야 하면 기존 이력을 수정하는 대신 반대 방향의 새 변동을 남긴다.

## 비즈니스 규칙

| 규칙 | 위반 시 사용자에게 일어나는 일 |
|---|---|
| 잔액 변경과 이력 기록은 항상 함께 일어난다 | 처리 중 문제가 생기면 잔액만 바뀌거나 이력만 남지 않고 전체가 실행 전 상태로 되돌아간다 |
| 보유 잔액보다 많은 포인트를 쓸 수 없다 | 회원이 잔액을 넘겨 사용하려 하면 포인트가 부족하다는 안내를 받고 주문이 진행되지 않는다 |
| 관리자도 보유 잔액을 넘겨 차감할 수 없다 | 포인트가 부족하다는 안내를 받고 잔액이 그대로 남는다 |
| 같은 회원의 잔액 변경 요청이 동시에 들어와도 차례로 처리된다 | 잔액 1,000P인 회원이 1,000P를 쓰는 주문 두 건을 동시에 넣으면 한 건만 접수되고, 나머지는 앞 건이 끝날 때까지 기다린 뒤 줄어든 잔액으로 판정받아 포인트가 부족하다는 안내를 받는다. 같은 잔액이 두 번 쓰여 잔액보다 많은 할인이 나가거나 잔액과 이력이 어긋나는 일은 없다 |
| 잔액은 마이너스가 될 수 없다 | 어떤 경로로도 잔액이 음수로 내려가지 않는다 |
| 결제 취소 시 적립분 회수는 남은 잔액만큼만 한다 | 회원이 적립분을 이미 써 버렸어도 결제 취소가 실패하지 않는다. 회수는 가능한 만큼만 이루어지고 환불은 정상 진행된다 |
| 포인트 정보가 없는 회원도 적립받을 수 있다 | 처음 적립 시 잔액 0인 정보가 자동으로 만들어져 적립이 정상 진행된다. 같은 회원에게 첫 적립이 동시에 여러 건 와도 정보는 하나만 만들어지고 모든 적립이 반영된다 |
| 포인트 정보가 없는 회원은 사용·차감·환불할 수 없다 | 포인트 정보를 찾을 수 없다는 안내를 받는다. 한 번도 포인트가 붙은 적 없는 회원에게 차감을 시도한 경우다 |
| 현장 결제 적립률은 10%로 고정되어 있다 | 회원이나 관리자가 적립률을 바꿀 수 없다. 변경하려면 시스템 설정 변경이 필요하다 |
| 환불 요청 접수만으로는 포인트가 움직이지 않는다 | 요청 단계에서 잔액이 바뀌지 않고, 취소가 확정될 때 한 번만 환급·회수가 이루어져 같은 금액이 두 번 반영되지 않는다 |
| 현장 결제만 결제 완료 시점에 적립된다 | 온라인 결제는 주문 접수 시점에 적립분이 결정되며, 결제 완료 시점에 다시 적립되지 않는다. 같은 결제로 두 번 적립되지 않는다 |
| 화면에 표시된 포인트 사용액과 서버 처리액이 일치해야 한다 | 다르면 포인트 할인 금액이 맞지 않는다는 안내를 받고 주문이 진행되지 않는다 |
| 포인트 사용과 주문 접수는 함께 처리된다 | 주문이 실패하면 포인트가 빠져나간 채 남지 않고 원래 잔액으로 되돌아간다 |
| 변동 종류는 적립·사용·환불 중 하나여야 한다 | 이력 조회 시 알 수 없는 종류로 걸러내려 하면 잘못된 포인트 유형이라는 안내를 받는다 |
| 이력은 수정·삭제되지 않는다 | 잘못된 변동을 되돌려도 원래 이력이 사라지지 않고, 반대 방향의 새 이력이 추가로 남는다 |
| 사유는 모든 변동에 남는다 | 관리자 수동 조정 시 사유를 반드시 입력해야 하며, 그 문구로 지급·차감 배경을 나중에 확인할 수 있다 |

## 다른 도메인과의 관계

**주문** — 포인트가 쓰이는 지점이다. 주문을 접수할 때 회원이 지정한 포인트가 잔액에서 차감되며, 그 금액이 쿠폰 할인과 함께 최종 결제 금액을 줄인다. 주문에는 이 주문으로 쓴 포인트와 적립될 포인트가 함께 기록되어, 나중에 결제가 취소될 때 환불·회수 금액의 근거가 된다.

**결제** — 포인트 적립과 회수를 촉발하는 지점이다. 현장 결제가 완료되면 결제 금액 기준으로 적립이 일어나고, 결제가 취소되면 쓴 포인트 환급과 적립분 회수가 함께 일어난다. 적립 금액 계산 기준은 결제 영역이 단일하게 갖고 있어, 주문에 기록된 적립 예정 금액과 실제 적립 금액이 갈리지 않는다.

**쿠폰** — 주문에서 포인트와 쿠폰은 나란히 적용되는 별개의 할인 수단이다. 하나를 쓰면 다른 하나를 못 쓰는 관계가 아니라 함께 쌓여 결제 금액을 줄인다.

**회원** — 포인트 잔액과 이력은 항상 특정 회원에게 귀속된다. 회원은 자기 포인트만 볼 수 있으며, 포인트 화면은 내 정보 영역의 일부로 제공된다.

**회원(추천인 보상)** — 가입할 때 추천인 닉네임을 입력하면 추천인과 신규 회원 양쪽에 각각 1,000포인트가 즉시 적립된다. 따라서 포인트가 늘어나는 경로는 현장 결제 적립, 관리자 수동 적립, 추천 보상 세 가지다. 추천 보상은 회원 영역이 직접 적립을 수행하지만 잔액과 적립 이력을 함께 남기는 방식은 다른 적립과 같다.

추천 보상은 **양쪽 포인트를 적립한 뒤에 추천 관계를 보상 완료로 넘긴다.** 순서를 뒤집어 완료 표시가 먼저 확정되면 "완료로 표시됐는데 포인트는 붙지 않은" 추천 관계가 남아 적립 실패 건을 상태만으로 가려낼 수 없다. 지금 순서라면 적립이 실패한 추천 관계는 보상 대기 상태에 그대로 머물러 재처리 대상으로 남는다. 다만 추천 등록 자체와 보상 적립은 서로 묶지 않는다 — 보상 적립이 실패해도 추천 등록은 되돌리지 않는 것이 의도된 선택이다.

## 사용자별 접점

### 일반 회원(웹)

- 사용 가능 포인트와 이번 달 소멸 예정 포인트를 확인한다.
- 포인트 내역 화면에서 잔액·소멸 예정액과 함께 적립·사용 이력 목록을 본다.
- 주문 화면에서 이번 주문에 쓸 수 있는 포인트를 확인한다.
- 주문할 때 포인트를 사용해 결제 금액을 줄인다.
- 현장 결제는 매장에서 값을 치르고 점주가 완료 처리하면 결제 금액의 10%가 자동으로 적립된다.
- 결제를 취소하면 썼던 포인트를 자동으로 돌려받는다.

### 관리자

- 특정 회원의 사용 가능 포인트와 이번 달 소멸 예정 포인트를 조회한다.
- 특정 회원의 포인트 적립·사용·환불 이력을 최신순으로 조회한다. 변동 종류로 걸러 볼 수 있고, 지정하지 않으면 전체가 보인다.
- 사유를 입력해 회원에게 포인트를 수동으로 적립한다.
- 사유를 입력해 회원의 포인트를 수동으로 차감한다. 보유 잔액보다 많은 금액은 차감할 수 없다.

### 점주

포인트 도메인에는 점주 전용 접점이 없다. 포인트는 서비스 전체 차원의 적립금으로 운영되며, 점주가 자기 가게 적립률을 정하거나 회원 포인트를 조정하는 기능은 제공되지 않는다.

### 0058. 포인트 잔액 변경은 POINT 행 비관적 락으로 직렬화한다

- 상태: 채택
- 결정 커밋: `18112f232` (2026-10-17)
- 대체한 결정: —
- 원문: 삭제 전 git 이력의 `docs/adr/0058-point-balance-pessimistic-lock.md`

#### 맥락

같은 기법을 결제 행에 먼저 적용한 결정은 [결정 0055](payment.md#decision-0055)입니다. 이 결정은 그것을 대체하지 않고, 대상을 포인트 잔액으로 넓힙니다.

- **lost update(갱신 손실)**: 두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 덮어써서, 한쪽 변경이 사라지는 현상입니다.
- **포인트 잔액**: `POINT` 테이블에 회원당 한 행이 있고(`member_id` UNIQUE), `available_points` 컬럼에 사용 가능 잔액을 담습니다. 잔액을 바꿀 때마다 `POINT_HISTORY`에 이력 한 줄이 함께 남습니다.

잔액을 바꾸는 경로는 다섯 개이고, 전부 `application-core`의 `PointLedgerService`를 거칩니다.

| 경로 | 호출부 |
|---|---|
| 주문 포인트 사용 | `OrderPlacementService#place` → `usePoints` |
| 관리자 차감·적립 | `PointDeductService`·`PointEarnService`(admin-application) |
| 결제 취소 환급·적립분 회수 | `PaymentEventListener#onPaymentCancelled` |
| 현장결제 적립 | `PaymentEventListener#onPaymentCompleted` |
| 추천 보상 | `ReferralRegisteredEventListener#handle` |

`PointPersistenceAdapter`는 잔액을 잠금 없이 읽었습니다. 도메인 `Point`가 계산을 마치면, 그 절대값을 엔티티에 복사하고 커밋 때 `UPDATE POINT SET available_points = <계산값>`을 실행했습니다. 그래서 잔액 1,000P인 회원이 1,000P를 쓰는 주문 두 건을 동시에 넣으면 이렇게 됩니다.

1. 두 트랜잭션이 둘 다 1,000을 읽습니다.
2. 둘 다 잔액 검사를 통과합니다.
3. 둘 다 0을 씁니다.

결과적으로 할인은 2,000P가 나가는데 잔액은 0이 되고, 이력에는 −1,000이 두 줄 남아 잔액과 이력이 어긋났습니다.

#### 이전 규칙

포인트 경로에는 동시성 제어가 없었습니다. 저장소의 잠금 규칙은 `backend/infrastructure/jpa/AGENTS.md` "규칙" 절의 비관적 락 항목(결정 0055)이었고, 이름은 `findByIdForUpdate`, 락 로드는 "그 트랜잭션의 첫 조회"로 정해져 있었습니다.

#### 결정

`PointLoadPort`의 잔액 로드를 비관적 락(PESSIMISTIC_WRITE)으로 바꾸고, 이름에 그 사실을 드러냅니다.

| 항목 | before | after |
|---|---|---|
| 포트 메서드 | `PointLoadPort#findByMemberId` | `PointLoadPort#findByMemberIdForUpdate` |
| 어댑터 쿼리 | `selectFrom … where … fetchOne()` | 같은 쿼리에 `.setLockMode(LockModeType.PESSIMISTIC_WRITE)` 추가 |
| 같은 회원 동시 요청 | 둘 다 같은 잔액으로 판정·덮어쓰기 | 두 번째 요청이 첫 요청 커밋까지 대기한 뒤 갱신된 잔액으로 판정 |
| 잔액 부족 응답 | 동시 요청이면 발생하지 않음 | 뒤 요청이 기존 `DomainErrorCode.POINT_INSUFFICIENT`를 받음(새 에러코드 없음) |
| 적립(`earnPoints`)의 행 확보 | 잠금 없는 로드, 없으면 새 행 저장 | `PointSavePort#saveIfAbsent`(원자적 upsert — `INSERT … ON DUPLICATE KEY UPDATE`)로 행을 보장한 뒤 잠금 로드 |
| `POINT`의 중복 인덱스 | `member_id` UNIQUE와 비유니크 `idx_point_member_id` 공존(`schema.sql`·`PointJpaEntity` 양쪽 선언) | `idx_point_member_id` 제거. 로컬·운영 DB는 `ALTER TABLE POINT DROP INDEX idx_point_member_id` 적용 필요 |
| 저장소 규칙 | 이름 `findByIdForUpdate`, 락은 언제나 첫 조회 | 이름 `find…ForUpdate`. "첫 조회" 조건은 락 뒤에 일반 조회로 다시 읽는 판정 값이 있을 때만 적용. "없으면 만든다" 경로는 원자적 upsert 후 잠금 로드. 여러 행을 한 트랜잭션에서 잠글 때는 키 오름차순 |

#### 근거

| 대안 | 채택하지 않은 이유 |
|---|---|
| 조건부 원자 UPDATE(`UPDATE … SET available = available - ? WHERE member_id = ? AND available >= ?` 후 영향 행 수 확인) | 잔액 검사가 도메인 `Point#deductPoints`에서 SQL로 새어 나갑니다. 또 회수(남은 잔액만큼만 차감 — `LEAST`), 적립, 최초 행 생성마다 전용 포트 메서드를 따로 만들어야 하고, 도메인 모델이 쓰이지 않는 경로가 생깁니다 |
| `@Version` 낙관적 락 | `POINT`에 `version` 컬럼을 추가하는 DDL이 필요합니다. 충돌하면 잔액이 충분한 요청도 실패하므로 재시도 루프와 에러 매핑을 새로 설계해야 합니다 |

비관적 락이 가장 단순합니다.

- 컬럼 변경과 도메인 로직 변경이 없고, 어댑터·포트와 적립의 행 확보 방식만 바뀝니다. 스키마 변경은 중복 인덱스 제거 하나입니다.
- 회원당 행이 하나이고 `member_id`가 UNIQUE라 InnoDB 레코드 락 하나만 잡히므로, 잠금 범위가 좁습니다.

#### 결과·감수한 손실

- **"첫 조회" 조건을 정확히 했습니다.** 결정 0055의 결제 경로는 락을 얻은 뒤 누적 합계를 일반 조회로 다시 읽으므로, 그 앞에 일반 조회가 있으면 스냅샷 때문에 경합이 통과합니다. 포인트는 판정 값(잔액)을 락 로드 자체가 읽습니다. `FOR UPDATE`는 locking read라 최신 커밋 값을 읽으므로, 주문 경로처럼 상품·쿠폰을 먼저 일반 조회한 뒤 잠가도 안전합니다. 이 차이를 규칙 문구에 반영했습니다.
- **적립은 원자적 upsert로 행을 보장한 뒤 잠급니다.** 가입 시 `POINT` 행을 만드는 코드가 없어, 모든 신규 회원의 첫 적립(추천 보상의 피추천인, 첫 현장결제)이 "행 없음" 경로를 탑니다. 이 경로의 방식을 네 가지 검토했습니다.
  - **곧장 잠금 로드**(처음 구현): 행이 없는 UNIQUE 키에 `FOR UPDATE`를 걸면 InnoDB(REPEATABLE READ)는 gap lock을 잡습니다. 신규 회원은 member_id가 가장 커서 그 gap이 대개 같은 `(최대 member_id, supremum)` 구간입니다. gap lock끼리는 호환되므로, **서로 다른** 신규 회원 두 명의 첫 적립이 겹치면 둘 다 gap lock을 잡은 뒤 INSERT의 insert-intention lock에서 상대를 기다려 데드락이 납니다. 추천 보상 리스너(`AFTER_COMMIT`)에서 나면 추천인·피추천인 보상이 함께 롤백되고 조용히 사라집니다. 리뷰에서 드러나 폐기했습니다.
  - **존재 확인 → 있으면 잠금 로드 / 없으면 INSERT**(두 번째 구현): 위 데드락은 피하지만, 행이 없는 **같은** 회원에게 적립 2건이 동시에 오면 둘 다 "없음"을 보고 INSERT해 한쪽이 `member_id` 유니크 위반으로 롤백됩니다. 변경 전부터 있던 유실이 그대로 남아 폐기했습니다.
  - **가입 시 행 생성 + 기존 회원 백필**: "회원당 POINT 행이 항상 있다" 불변식이 생기지만, 백필 DML 적용과 백필→배포 순서가 필요합니다. 또 member 컨텍스트 서비스는 point의 쓰기 포트를 직접 쓸 수 없어(`ServiceContextBoundaryTest`) 이벤트 리스너를 거쳐야 합니다. 채택하지 않았습니다.
  - **채택 — `saveIfAbsent` upsert 후 잠금 로드**: `INSERT INTO POINT … ON DUPLICATE KEY UPDATE member_id = member_id` 한 문장입니다. 키가 없으면 insert intention lock만 잡아 서로 다른 회원의 동시 생성이 막히지 않습니다. 같은 회원이 동시에 오면 뒤 트랜잭션이 앞의 미커밋 INSERT 행에서 기다렸다가 중복으로 처리되고, 이어지는 `FOR UPDATE`가 앞이 커밋한 값을 읽어 두 적립이 모두 반영됩니다. `ON DUPLICATE KEY UPDATE`는 중복 행에 exclusive next-key lock을 잡으므로 S→X 업그레이드 교착도 없습니다. 대가는 다음과 같습니다.
    - 어댑터의 MySQL 네이티브 문장 1개.
    - 행이 이미 있어도 적립마다 이 문장이 한 번 실행되는 비용(인덱스 조회 1회).
    - 중복으로 끝나도 AUTO_INCREMENT 값을 소비해 `POINT.id`에 빈 번호가 생깁니다(`BIGINT`라 고갈 위험은 없습니다).
    - next-key lock이 중복 행 바로 앞 gap도 잠그므로, 그 gap으로 들어오는 다른 회원의 첫 적립 INSERT가 커밋까지 기다릴 수 있습니다. 교착이 아니라 대기입니다.
- **사용·차감·환급·회수를 행이 없는 회원에게 하면 gap lock을 잠깐 잡습니다.** 바로 `POINT_NOT_FOUND`로 롤백되며 INSERT를 하지 않으므로 데드락을 만들지 않습니다. 그 사이 같은 gap에 들어오는 첫 적립 INSERT가 롤백까지 잠깐 기다릴 수 있습니다.
- **락 대기 타임아웃은 번역하지 않습니다.** `innodb_lock_wait_timeout`(기본 50초)을 넘기면 `CannotAcquireLockException`이 500으로 나갑니다. 결정 0055와 같은 상태입니다.
- **여러 회원의 행은 member_id 오름차순으로 잠급니다.** 한 트랜잭션에서 두 회원의 행을 잠그는 경로는 추천 보상 하나뿐입니다. 추천인은 기존 회원이고 피추천인은 방금 가입한 회원이라 추천인 → 피추천인 순서가 곧 오름차순입니다. 이 순서를 규칙으로 고정했습니다.
- **실제 DB 동시성은 Testcontainers 통합 테스트로 지킵니다.** `PointConcurrencyIntegrationTest`(MySQL 8.0 컨테이너, `backend/schema.sql` 전체 적재)가 다섯 가지를 검사합니다 — 동시 사용 직렬화, 잠금 대기 후 최신 값 읽기, 같은 회원 동시 첫 적립, 서로 다른 회원 동시 첫 적립, 잠금 조회의 UNIQUE 인덱스 사용과 중복 인덱스 부재. 락을 떼거나 upsert를 일반 INSERT로 바꾸면 앞의 세 시나리오가 실패하는 것을 확인했습니다.
  - Docker가 없는 환경에서 `./gradlew build`가 깨지지 않도록 `@Tag("integration")`으로 분리했고, `./gradlew :infrastructure:jpa:integrationTest`로 실행합니다. 대가로 이 태스크를 따로 돌리지 않으면 회귀를 잡지 못합니다.
  - 단위 테스트도 남깁니다. `PointPersistenceAdapterTest`는 `setLockMode(PESSIMISTIC_WRITE)` 호출을, `PointLedgerServiceTest`는 각 경로의 호출 순서(적립은 `saveIfAbsent` → 잠금 로드)를 검사합니다.
- **중복 인덱스 `idx_point_member_id`를 제거했습니다.** 옵티마이저가 비유니크 인덱스를 고르면 next-key·gap lock이 잡혀 잠금 범위가 넓어지기 때문입니다. `schema.sql`과 `PointJpaEntity`의 선언을 함께 지웠습니다. `ddl-auto: validate`는 인덱스를 검사하지 않으므로 부팅에는 영향이 없지만, 로컬·운영 DB에는 `ALTER TABLE POINT DROP INDEX idx_point_member_id`를 따로 적용해야 합니다.
